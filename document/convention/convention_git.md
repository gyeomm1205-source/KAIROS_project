# Git Convention

---

> **운영규칙**
> 
- 모든 작업은 이슈 생성 후 브랜치를 생성하여 진행하기
- PR 생성 시 최소 1명 이상의 승인이 있어야 머지 가능
- PR 생성 시 다른 팀원은 검토 후 승인 / 거부 / 코드 리뷰 진행하기
- **강제 머지**는 배포 장애 등 긴급 상황에서만 예외적으로 허용하며, 사후 보고하기
- 머지에서 필요없을 것 같은 브랜치는 미리 삭제하기
- 영어는 소문자로만 쓰

> **commit 메세지**
> 

```
[type/이슈키] 작업내용

ex) [feat/A506-20] 검색 결과 필터링 기능 추가
```

> **branch 이름**
> 

```
파트(be, fe, ai, infra 중 하나)/type/이슈키

ex) fe/feat/A506-20
```

> **Merge 이름**
> 

```
[파트/type] [이슈키] 작업내용

ex) [fe/feat] [A506-20] 호버 작성
```

> **Git Flow**
> 
- `main` : 배포 프랜치
- `develop` : 개발 브랜치
- `파트/type/이슈키` : 세부 개발 브랜치
    
    ex) fe/feat/A506-20
    

> **branch 종류**
> 

| Type | 의미 |
| --- | --- |
| ✨ `feat` | 새로운 기능 추가 |
| 🔨 `fix` | 버그, 오류 수정 |
| ✅ `chore` | 코드 외적인 설정이나 단순 파일 이동/삭제 (빌드 설정, 패키지 관리, 단순 주석/파일 이동 등)  
ex) .gitIgnore |
| 📝 `docs`  | 문서 수정(README나 WIKI 등 ) |
| ♻️ `refactor` | 기능은 그대로이되 코드 구조를 개선할 때 ex) 형식변경 |
| 💡 `test` | 테스트 코드 작업(테스트 코드, 리팩토링 등)  |
| 🔥 `!hotfix` | 긴급 장애 대응 (최우선 처리) |

> **label**
> 
- Organization 생성 시 추가! PR 작성 시 Label 항목 체크하기.

> **Issue**
> 

```
# ⚙️ ISSUE
- 어떤 이슈인지 설명

# 📄 To-Do
- [ ] 이슈에서 세부 todo list 작성
```

> **Pull Request**
> 

```
# 📄 Work Description
- 설명

# ⚙️ ISSUE
- close 이슈키
- ex) close A506-20

# 📷 Screenshot
 - 동영상, 사진, 로그 등등
 - ex) 큐알 성공 이미지, 스웨거, 포스트맨 등

# 💬 To Reviewers
리뷰어들에게 하고 싶은 말

# 🔗 Reference
문제를 해결하면서 도움이 되었거나, 참고했던 사이트(코드링크)
```

> **Code Review**
> 
- 커뮤니케이션 비용을 줄이기 위한 Pn 룰
    
    • P1: 꼭 반영해주세요 (Request changes)
    
    ```elixir
    리뷰어는 PR의 내용이 서비스에 중대한 오류를 발생할 수 있는 가능성을 잠재하고 있는 등 
    중대한 코드 수정이 반드시 필요하다고 판단되는 경우, P1 태그를 통해 리뷰 요청자에게 수정을 요청합니다. 
    리뷰 요청자는 p1 태그에 대해 리뷰어의 요청을 반영하거나, 반영할 수 없는 합리적인 의견을 통해 
    리뷰어를 설득할 수 있어야 합니다.
    ```
    
    • P2: 적극적으로 고려해주세요 (Request changes)
    
    ```elixir
    작성자는 P2에 대해 수용하거나 만약 수용할 수 없는 상황이라면 적합한 의견을 들어 토론할 것을 권장합니다.
    ```
    
    • P3: 웬만하면 반영해 주세요 (Comment)
    
    ```elixir
    작성자는 P3에 대해 수용하거나 만약 수용할 수 없는 상황이라면 반영할 수 없는 이유를 들어 설명하거나 
    다음에 반영할 계획을 명시적으로(JIRA 티켓 등으로) 표현할 것을 권장합니다. 
    Request changes 가 아닌 Comment 와 함께 사용됩니다.
    ```
    
    • P4: 반영해도 좋고 넘어가도 좋습니다 (Approve)
    
    ```elixir
    작성자는 P4에 대해서는 아무런 의견을 달지 않고 무시해도 괜찮습니다. 
    해당 의견을 반영하는 게 좋을지 고민해 보는 정도면 충분합니다.
    ```
    
    • P5: 그냥 사소한 의견입니다 (Approve)
    
    ```elixir
    작성자는 P5에 대해 아무런 의견을 달지 않고 무시해도 괜찮습니다.
    ```
    

> **GitLab – Jira 연동 규칙**
> 

GitLab과 Jira 연동을 위해

**commit / branch / merge request 중 최소 하나에 Jira Issue Key를 포함한다.**

### Issue Key 형식

```
프로젝트키-이슈번호
ex) A506-20
```

### 사용 예시

**commit**

```
[feat/A506-20] 검색 결과 필터링 기능 추가
```

**branch**

```
fe/feat/A506-20
```

**merge request**

```
[fe/feat] [A506-20] 검색 결과 필터링 기능 추가
```

이 규칙을 지키면 GitLab 작업이 Jira Issue에 자동 연결된다.
