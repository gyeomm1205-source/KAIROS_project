# 알고리즘 기술 설계서

# **KAIROS 알고리즘 기술 설계서**

## **1. 배경과 범위**

- KAIROS의 핵심 알고리즘은 사용자 활동을 구조화하고, 학습 상태를 계산하고, 그 결과로 추천·퀴즈·커리큘럼을 생성하는 일련의 규칙과 AI 파이프라인으로 구성된다.
- 본 문서는 MVP 기준 알고리즘 흐름, 점수 산식, 추천 규칙, 레벨 산정 정책, fallback 전략을 정의한다.
- AI 모델 호출이 포함되더라도 최종 상태 갱신과 추천 우선순위는 설명 가능한 규칙을 유지한다.

## **2. 현 상태와 목표 서비스**

### **현 상태**

- 저장소에는 추천/퀴즈/커리큘럼 알고리즘이 없다.
- Spring Boot와 FastAPI는 테스트용 연동 검증 수준이다.

### **목표 서비스**

- 외부 활동을 `user_activity`로 정규화한다.
- 활동 이벤트를 바탕으로 `learning_states`를 계산한다.
- 최근 활동, 학습 상태, 사용자 피드백, 히스토리 제외 컨텍스트, 캘린더 제약, Qdrant 검색 결과를 조합해 추천과 커리큘럼을 생성한다.

## **3. 전체 알고리즘 흐름**

```
외부 데이터 수집
-> 활동 정규화
-> user_activity 저장
-> learning_states 계산
-> 추천 또는 퀴즈 또는 커리큘럼 생성
-> 사용자 반응 수집
-> user_activity 추가 적재
-> learning_states 재계산
```

## **4. 활동 정규화 알고리즘**

### **입력**

- GitHub README, allowlist 설정 파일, 커밋 메타데이터
- Velog 글 제목/본문/태그
- Google Calendar 일정 제목/설명/시간
- 앱 내부 이벤트: 추천 클릭, 추천 무시, 퀴즈 제출, 커리큘럼 완료

### **처리 규칙**

1. 수집 텍스트에서 시크릿, 이메일, 전화번호, 토큰 패턴을 마스킹한다.
2. LLM 구조화 추출로 `category`, `tech_stacks`, `summary`, `confidence`를 생성한다.
3. `confidence`가 기준 미만이면 사람이 읽을 수 있는 짧은 요약만 저장하고 점수 반영 가중치는 낮춘다.
4. 결과를 `user_activity` 형식으로 저장한다.

### **출력 예시**

```json
{
  "source": "github",
  "category": "개발",
  "tech_stacks": ["Spring Boot", "JPA"],
  "summary": "Spring Boot와 JPA 기반 게시글 CRUD 프로젝트",
  "activity_date": "2026-03-05T09:00:00Z",
  "score_weight": 0.2
}
```

## **5. Learning State 계산 알고리즘**

## **5-1. 기본 공식**

기술별 원시 점수는 아래 식으로 계산한다.

```
Score(skill) =
Σ(ActivityWeight x TimeDecayWeight x ConfidenceWeight x FeedbackWeight)
+ SurveyBonus(skill)
```

### **항목 설명**

- `ActivityWeight`: 활동 종류별 기본 가중치
- `TimeDecayWeight`: 활동 시점이 오래될수록 줄어드는 감쇠치
- `ConfidenceWeight`: 구조화 추출 신뢰도 보정값
- `FeedbackWeight`: 추천 무시, 퀴즈 오답, 완료율 부족 등 후행 반응 보정값
- `SurveyBonus(skill)`: 온보딩 설문에서 직접 선택한 기술에 주는 초기 가산점

## **5-2. 기본 가중치 표**

| 이벤트 | 기본 가중치 |
| --- | --- |
| Velog 기술 글 작성 | 0.20 |
| GitHub README/설정 파일에서 기술 근거 발견 | 0.15 |
| GitHub 커밋 메타 기반 기술 활동 | 0.05 |
| 캘린더 학습 일정 수락 | 0.10 |
| 추천 클릭 | 0.05 |
| 추천 무시 | -0.02 |
| 커리큘럼 노드 완료 | 0.15 |
| 퀴즈 정답 | 0.20 |
| 퀴즈 오답 | 0.05 |
| 퀴즈 미응답 누적 | -0.03 |

## **5-3. Time Decay 규칙**

| 현재 시점과의 차이 | 가중치 |
| --- | --- |
| 0개월 | 1.0 |
| 1개월 | 0.9 |
| 2개월 | 0.8 |
| 3개월 | 0.7 |
| 4개월 | 0.6 |
| 5개월 이상 | 0.5 |

### **선택 이유**

- 구현이 단순하고 설명 가능하다.
- 월 배치 재계산과 잘 맞는다.

### **대안**

- 지수 함수 감쇠
- 활동 종류별 서로 다른 decay 곡선

### **트레이드오프**

- 계단형 감쇠는 단순하지만 현실의 연속적인 숙련도 감소를 정밀하게 반영하진 못한다.

## **5-4. 증분 반영과 월 배치 보정**

- 사용자 행동이 발생할 때는 관련 기술에 대해 증분 점수 반영을 수행할 수 있다.
- 월 1회 전체 `user_activity`를 기준으로 재계산해 drift를 보정한다.
- 재계산 결과는 `learning_states`에 upsert한다.

## **6. 레벨 산정 정책**

## **6-1. 1안: 고정 임계값**

예시 기준:

- `0.0~1.4`: 하
- `1.5~2.4`: 중
- `2.5 이상`: 상

### **장점**

- 가장 단순하고 설명이 쉽다.
- 초기 서비스에서 빠르게 도입할 수 있다.

### **단점**

- 기술별 활동량 차이와 사용자 분포를 반영하지 못한다.

## **6-2. 2안: 전체 사용자 백분위**

- 같은 기술을 가진 전체 사용자 점수 분포에서 위치를 계산한다.
- 예: `React 상위 18%`, `Spring 하위 40%`

### **장점**

- 객관적 비교 지표로 설득력이 높다.
- 성장 일지와 발표 시연에서 보여주기 좋다.

### **단점**

- 초기 사용자 수가 적으면 왜곡이 크다.
- 희귀 기술은 분포가 안정적이지 않다.

## **6-3. 3안: 개인 내 상대 비교**

- 한 사용자의 기술 목록 안에서 상대 순위를 계산한다.
- 예: `Vue = 하`, `R = 중`, `PyTorch = 상`

### **장점**

- 개인의 강점/약점 파악에 가장 직접적이다.
- 보완 추천과 우선순위 조정에 적합하다.

### **단점**

- 전체 사용자 대비 객관적인 위치를 알려주지 못한다.

## **6-4. 권장안: 2+3 조합**

KAIROS는 개인 맞춤성과 비교 지표를 모두 원하므로 `2안 + 3안` 조합을 권장한다.

### **운영 방식**

1. 먼저 raw score를 계산한다.
2. 기술별 전체 사용자 분포를 바탕으로 `population_percentile`을 계산한다.
3. 사용자 내부에서는 모든 기술을 점수순으로 정렬해 `relative_rank`를 계산한다.
4. `learning_states`에는 아래 값을 함께 저장한다.
    - `raw_score`
    - `level_absolute`
    - `population_percentile`
    - `level_percentile`
    - `relative_rank`
    - `level_relative`

### **활용 방식**

- `3안` 우선 사용:
    - 복습 추천
    - 약점 보완
    - 개인 성장 리포트
- `2안` 우선 사용:
    - 목표 포지션 대비 경쟁력 표시
    - 같은 기술 사용자 대비 상대 위치 안내
    - 도전 과제 또는 심화 추천

### **추천 엔진 결합 규칙**

- 개인 내 하위권이면서 전체 백분위도 낮은 기술:
    - 가장 강한 보완 추천 대상
- 개인 내 상위권인데 전체 백분위도 높은 기술:
    - 심화 추천 또는 포트폴리오 추천 대상
- 개인 내 상위권이지만 전체 백분위는 낮은 기술:
    - 학습량은 많지만 시장 기준 숙련도가 부족할 수 있으므로 실전 문제 또는 공식 문서 추천
- 개인 내 하위권이지만 전체 백분위는 높은 기술:
    - 사용자의 학습 편중 가능성이 있으므로 핵심 기초 복습 추천

### **장점**

- 사용자 입장에서 "내 안에서 약한 것"과 "남들과 비교해 부족한 것"을 모두 볼 수 있다.
- 추천 이유 설명이 쉬워진다.

### **단점**

- 계산 비용과 UI 설명 복잡도가 올라간다.
- 초기 사용자 수가 적을 때 `2안`은 보조 지표로만 써야 한다.

## **7. 최초 분석 알고리즘**

1. 설문 정보와 외부 연동 범위를 입력받는다.
2. GitHub, Velog, Google Calendar 데이터를 수집한다.
3. 정규화된 활동 이벤트를 생성해 `user_activity`에 저장한다.
4. 기술별 점수를 계산해 `learning_states`에 반영한다.
5. 상위 기술, 반복 기술, 최근 활동 공백, 추천 포지션을 요약한다.
6. 사용자가 `네/아니오` 피드백을 남기면 다음처럼 처리한다.
    - `네`: 최초 추천 생성 단계로 이동
    - `아니오`: 교정 피드백 저장 후 재분석

## **8. 추천 알고리즘**

## **8-1. 입력 순서**

추천 생성 시 아래 순서로 컨텍스트를 조합한다.

1. 최근 `user_activity`
2. `learning_states`
3. 사용자 프로필과 목표 포지션
4. `history exclusion`
5. Google Calendar 일정 제약
6. Qdrant 검색 결과

## **8-2. 추천 우선순위 규칙**

### **학습 추천**

- 최근 30일 활동과 이어지는 기술을 우선한다.
- 개인 내 하위권 기술을 보완하되, 목표 포지션 핵심 기술이면 가중치를 더 준다.
- 이미 제외된 히스토리와 충돌하는 맥락은 제거한다.

### **레퍼런스 추천**

- Qdrant에서 `skill`, `topic`, `source_type`, `freshness_grade` 필터로 후보를 가져온다.
- 후보 문서 중 공식 문서와 고신뢰 기술 블로그를 우선한다.
- outdated 가능성이 있으면 결과에 경고를 포함한다.

### **새 학습 시작 추천**

- 사용자가 자연어로 입력한 목표를 기술 스택 후보로 분해한다.
- 관련 기술의 현재 점수가 거의 없으면 사전 퀴즈를 먼저 제안한다.

## **8-3. 추천 출력 규칙**

모든 추천에는 아래 필드를 포함한다.

- `reason`
- `references[]`
- `assumptions[]`
- `next_actions[]`

## **9. 레퍼런스 검증 알고리즘**

1. 추천 후보 URL이 allowlist 또는 검증된 도메인인지 확인한다.
2. Qdrant payload의 `published_at`, `source_type`, `allowed`를 확인한다.
3. LLM 요약 단계에서 다음 3가지를 판정한다.
    - 현재 추천 주제와 관련 있는가
    - 과도하게 오래된가
    - 사용자 수준에 맞는가
4. 검증 결과를 `reference_validation_report`로 저장한다.

## **10. 퀴즈 알고리즘**

### **10-1. 사전 퀴즈**

- 신규 학습 주제 시작 전 기초 수준을 파악한다.
- 점수가 거의 없는 기술을 대상으로 한다.

### **10-2. 복습 퀴즈**

- 최근 완료한 커리큘럼 노드와 추천 레퍼런스를 기반으로 생성한다.

### **10-3. 채점 반영**

- 정답은 `+0.20`, 오답은 `+0.05`, 미응답 누적은 `0.03`
- 정답률이 낮으면 다음 추천에서 난이도와 학습량을 낮춘다.
- 정답률이 높으면 심화 레퍼런스와 확장 커리큘럼을 제안한다.

## **11. 커리큘럼 생성 알고리즘**

1. 최근 활동과 현재 learning state를 조회한다.
2. 캘린더의 이미 존재하는 일정과 충돌 가능한 날짜를 제외한다.
3. 추천 대상 기술 중 우선순위가 높은 항목을 선정한다.
4. 5일 또는 1주 단위 노드로 분해한다.
5. 각 노드에 `estimated_minutes`, `goal`, `reference_ids`, `quiz_needed`를 붙인다.
6. 사용자가 수락하면 캘린더 업로드 대상이 된다.

### **배치 규칙**

- 평일 저녁 중심으로 짧은 학습 노드를 우선 배치
- 중요한 외부 일정 전날에는 새로운 학습보다 복습 노드를 우선
- 일정 충돌 시 자동 삭제하지 않고 backlog 후보로 남긴다

## **12. 예외와 fallback**

| 상황 | 대응 |
| --- | --- |
| 외부 데이터가 거의 없음 | 설문 기반 최소 점수와 일반 추천 세트 사용 |
| GitHub는 있으나 Velog 없음 | 코드/README 기반 분석 비중을 높임 |
| Qdrant 검색 실패 | 기본 큐레이션 문서 집합으로 fallback |
| 추천 편향 누적 | 최근 3회 추천 기술 다양성 규칙 적용 |
| 사용자가 반복적으로 추천 무시 | 동일 기술 추천 강도를 낮추고 다른 접근 제안 |
| 캘린더가 꽉 참 | 학습 노드 길이를 줄이거나 backlog 추천으로 전환 |

## **13. 고도화/대안**

### **13-1. 고도화 후보**

- 기술 간 선행 관계 그래프 도입
- reranker 도입
- quiz difficulty adaptive tuning
- 사용자의 피로도 지수 기반 톤/난이도 조절

### **13-2. 대안으로 유지할 수 있는 단순 정책**

- 초기에는 1안 절대 임계값만 UI에 보여주고, 내부 계산에만 2+3을 쓰는 단계적 도입
- low confidence 활동은 추천 입력에서 제외하고 히스토리 표시만 하는 보수적 운영
