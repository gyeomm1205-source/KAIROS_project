# AI 개발 기록

> KAIROS 프로젝트에서 AI 파트를 담당하며 설계/구현한 내용을 정리한 문서입니다.

---

## 담당 역할

팀 5명 중 **AI 전담**으로, RAG 기반 추천 엔진, AI 커리큘럼/퀴즈 생성, 프로필 분석 파이프라인을 설계 및 구현했습니다.

### 담당 모듈

| 모듈 | 파일 | 설명 |
|---|---|---|
| 학습 추천 엔진 | `recommendation_svc.py` | Qdrant 벡터 검색 + GPT-4o RAG 추천 (일일 배치 + 온디맨드) |
| 커리큘럼 생성 | `curriculum_svc.py` | 3가지 모드 커리큘럼 생성 + Google Calendar 일정 고려 |
| 퀴즈 생성 | `quiz_svc.py` | Qdrant 청크 기반 퀴즈 + 채점 루브릭 단일 호출 생성 |
| 프로필 분석 | 분석 파이프라인 | GitHub/Velog 데이터 수집 → LLM 분류 → 개발자 프로필 생성 |
| 데이터 인제스천 | 임베딩 파이프라인 | 문서 청킹 → 벡터 임베딩 → Qdrant 적재 (중복 제거 포함) |

### 핵심 설계 원칙

**1. Pydantic 구조화 출력**
- 모든 LLM 호출에 `with_structured_output(PydanticModel)` 적용
- JSON 파싱 실패 제로, 타입 안전성 확보
- 문자열 파싱 없이 스키마 기반으로 LLM 응답을 직접 검증

**2. Graceful Degradation**
- 모든 LLM/Qdrant 호출에 폴백 응답 정의
- OpenAI API 장애나 타임아웃 시에도 서비스 중단 없이 기본 응답 반환
- AI 실패가 전체 서비스 장애로 전파되지 않도록 격리

**3. 환각 방지 (Anti-Hallucination)**
- 퀴즈 출제 시 Qdrant에서 검색된 청크만을 근거로 사용
- 프롬프트에서 청크 범위 외 내용으로 문제 생성을 명시적으로 차단
- 근거 없는 문제 생성률 0%

**4. 단일 호출 최적화**
- 퀴즈 문제와 채점 루브릭을 하나의 Pydantic 모델로 정의하여 1회 LLM 호출로 동시 생성
- 2회 호출 대비 LLM 호출 횟수 50% 감소, 퀴즈-루브릭 일관성 보장
- 실패 시 2회 호출 순차 방식으로 자동 폴백

## 기술적 의사결정 기록

<details>
<summary><b>TDR 1: 추천 및 퀴즈에 RAG 패턴 적용</b></summary>

**배경:** LLM은 사용자 개인의 학습 이력과 활동 데이터를 모름

**선택지:**
| 방식 | 장점 | 단점 |
|---|---|---|
| Fine-tuning | 도메인 특화 가능 | 사용자별 모델 불가능, 비용 높음, 데이터 갱신 시 재학습 필요 |
| **RAG** | 실시간 데이터 반영, 비용 효율적 | 검색 품질에 의존 |
| 프롬프트 전체 삽입 | 구현 단순 | 토큰 한계, 비용 급증 |

**결정:** RAG — 사용자 데이터를 Qdrant에 임베딩하고, 검색된 청크를 LLM 컨텍스트로 제공

**결과:** 데이터 업데이트 시 재학습 없이 실시간 반영, 토큰 비용 절감

</details>

<details>
<summary><b>TDR 2: 퀴즈 환각 방지 설계</b></summary>

**배경:** LLM이 자체 지식으로 퀴즈를 만들면 학습 자료와 무관한 문제가 생성될 수 있음

**선택지:**
- (A) 생성 후 후처리 필터링 → 이미 생성된 후라 비용 낭비
- (B) 프롬프트로만 제약 → 완벽한 통제 불가
- **(C) Qdrant 청크 기반 근거 강제 → 검색된 자료만 프롬프트에 삽입하고, 범위 외 출제 차단**

**결정:** (C) — 퀴즈 생성 시 반드시 Qdrant에서 관련 청크를 검색하고, 해당 청크 내용만을 근거로 출제하도록 프롬프트 설계

**결과:** 근거 없는 문제 생성 차단, 학습 자료와 퀴즈의 일관성 보장

</details>

<details>
<summary><b>TDR 3: Pydantic 구조화 출력 (vs JSON 수동 파싱)</b></summary>

**배경:** LLM의 JSON 응답이 간헐적으로 잘리거나 형식이 달라지는 문제

**선택지:**
- (A) `json.loads()` + 수동 키 검증 → 에러 처리 코드 폭증
- **(B) LangChain `with_structured_output(PydanticModel)` → 스키마 기반 자동 검증**

**결정:** (B) — 모든 LLM 호출에 Pydantic 모델을 출력 스키마로 지정

**결과:** JSON 파싱 에러 제거, 타입 안전성 확보, 서비스 코드 간결화

</details>

<details>
<summary><b>TDR 4: 퀴즈 + 루브릭 단일 호출 생성</b></summary>

**배경:** 퀴즈를 생성한 후 별도로 채점 루브릭을 생성하면 2회 LLM 호출 필요 → 비용과 지연 증가

**결정:** 하나의 Pydantic 모델에 퀴즈 문제와 채점 루브릭을 함께 정의하여 1회 호출로 동시 생성. 실패 시 2회 순차 호출로 폴백.

**결과:** LLM 호출 횟수 50% 감소, 퀴즈-루브릭 간 일관성 보장, 폴백으로 안정성 유지

</details>

<details>
<summary><b>TDR 5: 듀얼 커리큘럼 (약점 보완 vs 강점 강화)</b></summary>

**배경:** 사용자마다 학습 전략이 다름 — 부족한 부분을 채우고 싶은 사람과 강점을 더 키우고 싶은 사람

**결정:** AUTO 모드에서 약점 보완 커리큘럼과 강점 강화 커리큘럼 두 가지를 `asyncio.gather`로 병렬 생성하여 동시 제공

**결과:** 사용자에게 선택권 부여, 병렬 처리로 응답 시간 증가 최소화

</details>

<details>
<summary><b>TDR 6: Google Calendar 연동 날짜 인식 스케줄링</b></summary>

**배경:** AI가 생성한 커리큘럼 일정이 사용자의 기존 일정과 충돌하면 실행 불가

**결정:** Google Calendar API에서 기존 일정(busy 시간대)을 조회하고, 비어있는 날짜에만 학습 노드를 배치

**결과:** 현실적으로 실행 가능한 학습 계획 생성

</details>

<details>
<summary><b>TDR 7: Graceful Degradation 폴백 설계</b></summary>

**배경:** OpenAI API 장애/Qdrant 다운 시 서비스 전체가 중단되면 안 됨

**결정:** 모든 AI 호출(LLM, 벡터 검색)에 try-except + 사전 정의된 기본 응답 반환. AI 실패가 Spring Boot 쪽으로 전파되지 않도록 격리.

**결과:** AI 장애 시에도 서비스 가용성 유지

</details>
